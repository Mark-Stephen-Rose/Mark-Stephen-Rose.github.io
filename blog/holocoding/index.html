Building the Database Behind HoloCoding

Django PostgreSQL Testing Open Source

For my senior capstone at Stonehill College, our class built HoloCoding, a free, open-source web application for qualitative data analysis. Researchers upload documents, highlight passages, and tag them with codes, then pull every passage under a code back up to look for patterns. It also exports codebooks, spreadsheets and annotated documents.

I led a team of three on the database side of the project, and that is the part I want to write about.

The layer everything else stands on

Our team was responsible for the data models, the logic behind them, and the connection between the database and the backend server. Every document, highlight and code in the app passes through that layer, so the goal was for it to be boring in the best way: predictable, well tested, and easy for the rest of the class to build on without worrying about what was underneath.

The stack is Django with PostgreSQL, so much of the work was deciding how to represent the data cleanly and making sure the backend could read and write it reliably as the frontend and export features grew around it.

Learning to build as a group

The hardest part was not any single technical problem. It was working on a large project with a lot of people. We used pair programming and test-driven development, and both took a lot of getting used to. Writing the test before the code, and talking through every decision with a partner instead of heading off alone, felt slower at first.

Over time it changed how I think about shared code. A test is a written agreement about how something should behave, which matters when other teams depend on what you build. I came away more comfortable explaining my reasoning out loud, and more patient with the unglamorous work that makes a codebase trustworthy.
